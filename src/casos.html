caso 1

Founder que codea — de sistema DIY a plataforma delegable

Contexto

Founder técnico que construyó el producto él mismo durante 3 años. Sistema en PHP puro con JavaScript vanilla, sin framework, sin tests, sin CI/CD. El negocio tenía clientes reales facturando, pero el founder era el único que entendía el código y estaba al borde del burnout.

Problema

Deploys manuales los domingos a la noche "por las dudas". Cualquier cambio en el core requería 3 días de pruebas manuales. Contratar un dev era imposible porque nadie quería tojar ese código. La cloud bill crecía sin control porque todo estaba en el mismo servidor.

Foco de intervención

Auditoría de 48h para identificar los 3 módulos más críticos. Refactorización incremental con Strangler Fig: primero el módulo de facturación (el que más cambios recibía), luego el de usuarios. Se agregó CI/CD básico, tests en los módulos nuevos y se separaron responsabilidades en servicios independientes.

Lecciones aprendidas

No hace falta refactorizar todo para ver mejora. Con los primeros dos módulos refactorizados, el founder pudo delegar desarrollo de features no críticas a un dev freelance sin miedo a romper producción.

caso 2

Equipo pequeño con monolito heredado — del espagueti a los módulos

Contexto

Equipo de 5 devs manteniendo un monolito .NET Framework 4.6 construido por una agencia que ya no existía. Nadie del equipo original quedaba. La documentación era inexistente y el código no tenía tests.

Problema

Incidentes recurrentes cada vez que tocaban el core. Cloud bill de $12k/mes sin justificación. Deploys de 4 horas los viernes a la noche. El equipo pasaba el 70% del tiempo apagando incendios y el 30% construyendo producto.

Foco de intervención

Se realizó un mapeo de boundaries del dominio y se identificaron los módulos con mayor tasa de cambio. Se migró a .NET 8 con Modular Monolith como paso intermedio, manteniendo el monolito original funcionando en paralelo. Se implementó pipeline de CI/CD con tests automatizados y rollback en segundos.

Lecciones aprendidas

Migrar a .NET 8 no fue el desafío técnico más grande — lo fue romper el acoplamiento implícito entre módulos. El Modular Monolith dio el equilibrio justo entre orden y velocidad sin la complejidad de microservicios.

caso 3

Proyecto IA/no-code que se volvió crítico — de prototipo a sistema serio

Contexto

Una agencia pequeña armó su plataforma interna de gestión de proyectos con una herramienta no-code + scripts en Python generados con ChatGPT. La usaban para gestionar sus propios proyectos y, eventualmente, sus clientes empezaron a depender de ella.

Problema

La plataforma se caía cada vez que subían de 50 usuarios concurrentes. Las integraciones con APIs externas eran frágiles (sin timeout, sin retry, sin circuit breaker). No había forma de auditar cambios. Cualquier modificación requería volver a ChatGPT y rezar.

Foco de intervención

Se identificaron los 3 flujos críticos: autenticación, gestión de proyectos y reportes. Se reimplementaron en .NET 8 con arquitectura hexagonal, manteniendo el frontend no-code funcionando contra las nuevas APIs. Se agregaron patrones de resiliencia (retry, circuit breaker, bulkhead) y monitoreo básico.

Lecciones aprendidas

No-code + IA son excelentes para prototipar, pero cuando el negocio depende del sistema, necesitás arquitectura. La transición puede ser gradual: el frontend no-code sigue funcionando mientras el backend se profesionaliza.
